# Evaluation harness

The part of this repository that makes the difference. Most portfolio projects
have a demo. Very few have numbers.

## Why this exists

LLM systems are non-deterministic and they regress silently. "I tried it and it
worked" is not evidence — the same question can produce a different answer on the
next call, and a prompt change that helps one case can break three others with
nothing visibly failing.

A fixed question set with known answers, run automatically and scored, is what
turns "it seems good" into "82%, and here are the five failures".

## Running it

```bash
python evals/run_eval.py --provider groq --runs 3 --max-cost 5.00
```

Writes `evals/results/RESULTS.md` — a real markdown table, generated by the
script. **You never hand-type a number into a README.** That rule is the whole
point: a number you typed is a number you could have got wrong or rounded
generously, and neither you nor a reader can tell afterwards.

## What is measured, and why each

| Metric | The question it answers |
|---|---|
| **Accuracy** | Is the number right, within tolerance? |
| **Refusal correctness** | Does it know what it *cannot* answer? |
| **Citation rate** | Can the user check the answer themselves? |
| **Tool calls per question** | Is it efficient, or flailing? |
| **Latency p50/p95** | Is it usable? |
| **Cost per question** | Does this survive contact with a budget? |
| **Variance across runs** | Is the result stable, or did you get lucky once? |

**Why 3 runs.** It separates *capability* failures (the model cannot do this)
from *reliability* failures (it can, but not consistently). Those are different
problems with different fixes, and a single run cannot tell them apart.

## The question set

25 questions in `gold.yaml`, deliberately uncomfortable:

| Category | Count | Purpose |
|---|---|---|
| Straightforward lookups | 8 | Baseline competence |
| Comparisons needing fiscal-year normalization | 6 | The trap that produces plausible wrong answers |
| Genuinely ambiguous | 5 | Does it ask, or guess? |
| **Should be refused** | 4 | Does it know its limits? |
| Involving restated figures | 2 | Does it surface that the number changed? |

## Before your first run: verify the expected values

Every `expected_value` in `gold.yaml` is marked `# VERIFY THIS`, except NVIDIA's
FY2024 revenue (60,922,000,000 — confirmed against NVIDIA's published FY2024
results).

**Verify each one against the actual filing before you trust any result.** An
eval scored against wrong expected values is worse than no eval: it reports
confident numbers that mean nothing, and you will not find out until someone
asks you about a specific question in an interview.

This is tedious and it is the highest-value hour in the project.

## Reporting the results

**Report the failures.** In the README, in your resume line, in the interview.

"82% accuracy, and the five failures cluster into two root causes" is read as
competence. "100%" is read as either untested or untrue — and the person reading
it has seen enough portfolios to know which.

When a question fails, work out *why* before you change anything. Two of these
are much more interesting than the other:

- the tool returned wrong data → a bug in the server
- the tool returned right data and the model misread it → a prompt or tool-description problem
- the expected value in `gold.yaml` was wrong → fix the test, and note that you found it
